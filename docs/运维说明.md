# 部署与运维

本文描述 `172.29.20.105` 的专用 Docker 部署。官网主机 `172.29.20.85` 使用现有 Kubernetes，参见 [服务器 85 部署](服务器85部署.md)。

独立部署在 `/opt/mbti-site`，入口端口 8086；PostgreSQL 5432 和 API 8091 只监听回环地址。此部署不依赖原工作区的实验室网站。

## 运行结构

```text
/opt/mbti-site/
  .env                 实际应用密钥，权限 600，不进入 Git
  current -> releases/<版本>
  previous-release     上一个源码目录（第二次发布后出现）
  releases/            源码、生产前端和离线 wheels
  runtime/docker/      Docker 静态运行时
  docker-data/         镜像、容器和 PostgreSQL 命名卷
  backups/             排除临时答案的数据库备份
```

专用服务器是 CentOS 7 / 3.10 内核，已采用实测兼容的 Docker 26.1.4、Compose 2.39.4、vfs 存储和 host 网络。保持 SELinux Enforcing。系统版本较旧，后续建议迁移受维护的操作系统，并使用当前受支持的 Docker 和默认隔离网络。新系统不必沿用此兼容配置。

首次安装只适用于空闲专用主机：解压官方 Docker 静态包至 `runtime/docker`，安装官方 Compose 插件到 `/root/.docker/cli-plugins/docker-compose`，核对官方校验和，再运行 `deploy/install-runtime.sh`。该脚本创建此项目的 daemon 配置和 systemd 服务，不应直接用于已有其他容器业务的主机。

## 准备离线发布

联网开发机执行 `npm ci`、`npm run build`，用 Python 3.12 的 pip 根据 `backend/requirements.lock` 下载 Linux amd64 wheels 至 `.offline/wheels`，见 `deploy/prepare-wheels.sh`。准备并加载三个 linux/amd64 基础镜像：`python:3.12-slim-bookworm`、`postgres:17-bookworm`、`nginx:1.28-alpine`。镜像、wheelhouse 和构建产物属于交付包，不进入源码仓库。

创建新的 `releases/<版本>`，复制源代码、`frontend/dist` 和 `.offline/wheels`；创建根目录 `.env`（参考 `.env.example`），使用独立随机后台密码、数据库密码和至少 32 字符的 SECRET_KEY。数据库密码用随机十六进制，避免 URL 编码歧义。私密文件权限 600。

```sh
/opt/mbti-site/releases/<版本>/deploy/release.sh /opt/mbti-site/releases/<版本>
cp /opt/mbti-site/current/deploy/mbti-site.service /etc/systemd/system/
cp /opt/mbti-site/current/deploy/mbti-backup.* /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now mbti-site mbti-backup.timer
```

首次启动创建管理员和初始题库。修改 `.env` 中初始后台密码不会覆盖数据库已有密码，正常改密请用后台。

## 检查与日志

```sh
curl -f http://127.0.0.1:8086/healthz
/opt/mbti-site/runtime/docker/docker compose --project-directory /opt/mbti-site/current --env-file /opt/mbti-site/.env ps
systemctl status mbti-docker mbti-site mbti-backup.timer
/opt/mbti-site/runtime/docker/docker compose --project-directory /opt/mbti-site/current --env-file /opt/mbti-site/.env logs --tail 100 api web
```

Nginx / API 不记录请求访问日志，避免采集答案或续答凭证。API 错误只写服务诊断，不接入外部追踪。代理仅信任本机 Nginx，登录、计分和续答接口有限流。后台 HttpOnly、SameSite Strict Cookie 配合来源校验和 CSRF。当前单个 API 进程，限流为进程内实现；扩容需共享限流及清理锁。

临时草稿在服务端加密、凭证只存哈希；链接凭证位于 URL fragment，恢复时清除地址栏片段。7 天失效；完成 / 主动撤销删除；每 5 分钟清理过期数据。链接持有人可以恢复草稿，应仅在可信设备使用。HTTP 是本次内网入口，跨公网使用应先配置 HTTPS，并设置 `COOKIE_SECURE=true` 与正确的 `PUBLIC_ORIGIN`。

## 备份与恢复

每天服务器当地时间 03:15 执行 `mbti-backup.timer`。备份含问卷、管理员密码哈希、匿名事件、审计日志；**不含续答临时答案与后台会话内容**。文件权限 600，目录仅管理员可访问。敏感配置 `.env` 独立安全保管，不随数据库备份上传仓库。备份建议由管理员定期转存、轮换，不通过本项目自动发往第三方。

```sh
/opt/mbti-site/current/deploy/backup.sh
# 恢复会替换应用数据库内容并使旧后台会话失效，先保留现状备份。
/opt/mbti-site/current/deploy/restore.sh /opt/mbti-site/backups/atlas-<时间>.dump
```

可先用 `createdb` 和 `pg_restore` 在独立临时数据库验证备份，不影响线上数据。应用重启保留命名卷中的管理内容；浏览器草稿独立于服务重启。

## 更新与回滚

发布前备份数据，为新版本镜像设置独立 `RELEASE_TAG` 并保留旧值、旧镜像和旧 release。`release.sh` 先构建，再切换 current 并等待健康。部署失败时恢复旧 `RELEASE_TAG` 和 current，执行 `compose up -d --no-build --wait`；若存在不兼容数据库迁移，需按迁移说明恢复备份。首版仅自动建表，不包含破坏性迁移。

服务开机自启依赖 `mbti-docker` 和 `mbti-site`。正常维护可执行 `systemctl restart mbti-site`；不要执行 `docker compose down -v`，这会删除数据库卷。新域名 / 证书、流量入口和网络映射应在相应网络管理员管理的边界内配置。
